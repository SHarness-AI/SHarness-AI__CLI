# v0.2.0: what we ask to be confirmed (released 29 Oct 2026)

The first release that carries the experiments and the three MVPs (board R7). Run [`RELEASE.md`](RELEASE.md)
first, then these. Each was tested by its author, in CI, and by security@; none has yet been confirmed by
someone who did not write it. Answer as [`README.md`](README.md) says.

| Id | Who | What changed | Do | Expect |
|---|---|---|---|---|
| Q0.2.0-1 | N | The README is the PyPI page | Follow the PyPI page's quick start word for word on a fresh machine | Every command works as written. Anything missing or out of order is *Confusing* |
| Q0.2.0-2 | N | macOS says what is missing (issue #6) | On a Mac: `sharness-ai probe`, `sharness-ai run --policy p.json -- ls`, `sharness-ai hello` | probe prints each Linux-only row as `n/a (macOS: …)`; run and hello refuse in one line naming macOS, exit 126, nothing runs. **Checked so far only with a faked platform; a real Mac is the ask** |
| Q0.2.0-3 | N | The capabilities label (issue #8) | `sharness-ai probe` as a normal user, then as root | As a user: `none in effect`, with the bounding set shown separately. As root: `all in effect` |
| Q0.2.0-4 | N | A refusal names its error (issue #8) | `sharness-ai hello --json` | Each refused probe's `got` names the error (`PermissionError`, `MemoryError`, …), never a fragment of text from the bottom of the screen |
| Q0.2.0-5 | B | The first door, `sharness.fs` | `sharness-ai session new`, `sharness-ai fs serve --target disk --root ./work`, then write, append, read and list through it (`sharness-ai fs --help`) | Writes land under `./work` only; a path that climbs out is refused (`within_root`); `GET /v0/hello` says the door is a Setting until the launcher exists |
| Q0.2.0-6 | B | Binary files read back (board T25, item 5) | Write a file of bytes that are not text (an image) through the door, then read it | `--json` returns `content_b64` that decodes to exactly the bytes written |
| Q0.2.0-7 | S | A secret split across appends is refused (T25, item 3) | Append a private-key header to a file through the door in two pieces | The second append is refused (`refuse_secrets`). Then try to beat it: pieces far apart, other encodings. Report what got through; the door's `REALITY.md` names what is not covered |
| Q0.2.0-8 | B | `contain`'s wording (T25, item 6) | `sharness-ai contain --workspace . --sites github.com --dry-run -- x` | The held line does not say "nothing else is reachable"; the next line says github.com is held as port 443 only |
| Q0.2.0-9 | B | The shell under the harness (E13) | As root on Linux: `sharness-ai shell --sites pypi.org`, then inside: `pip download` something from pypi.org, `curl https://example.com`, and a write outside the workspace | pypi.org works; example.com and the write are refused, each saying who refused; on exit, the summary says what was undone |
| Q0.2.0-10 | S | The shell reaches only its proxy (security review 2, SR-28) | Inside `sharness-ai shell`: connect to the proxy's port on another address (`127.0.0.2`, another host), send DNS and other UDP | All refused or with no route. Inside, `run` says the namespace is loopback only and does not say DNS still resolves |
| Q0.2.0-11 | S | Nothing of the shell outlives it (SR-30) | Inside `sharness-ai shell`: start a background job that keeps writing to the workspace, then exit | The job is gone, the shell's user is removed, and the summary says if anything could not be undone |
